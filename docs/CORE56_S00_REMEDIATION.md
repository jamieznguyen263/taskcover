# Sprint S00 — Core 56 Portfolio Hygiene & Safety

Status: implementation + dry-run validation complete. **No database writes have been made.** Staging `--write` mode is implemented and unit-tested but has not been executed against any real database this sprint (see "Environment identity" below).

## 1. What this sprint is

The 56 Core English articles (`TC-001`–`TC-056`, `creation_key = core56-tc-###`) were bulk-authored through a Claude-batch pipeline (`docs/core56-claude-batches/`, `scripts/core56-*.ts`) and are marked `published` in `docs/core56-claude-batches/publication-tracker.csv`. Sprint S00 builds a read-only audit and a safe, reviewable remediation pipeline for the *mechanical* hygiene defects across that corpus — leaked internal workflow language, duplicated Direct Answer paragraphs, redundant FAQ presentations, un-rendered markdown tables — without rewriting content, inventing facts, or touching anything immutable.

This sprint does **not**: rewrite articles, add missing assets/visuals, change slugs, change `factCheckStatus`, or publish/approve anything.

## 2. Architecture summary

- **Content model**: `src/content/insights.types.ts` — `InsightArticle`/`InsightBlock`. Draft vs. published is a DB-level distinction: `insight_article_localizations.draft_snapshot` (editable) vs. `.published_snapshot` (live; the public site and sitemap read only this) vs. append-only `insight_article_revisions` (immutable, never rewritten — [`repository.ts`](../src/lib/admin/repository.ts)).
- **Editability**: an article must be in `draft` status for `saveArticleDraft` to touch it; a `published` article can be reopened to `draft` (`article:edit` permission — [`permissions.ts`](../src/lib/admin/permissions.ts)) without disturbing what's currently live, since `publishedSnapshot` is only overwritten at the next real publish.
- **Publish QA** (`src/lib/insights/publish-qa.ts`) does not gate on `factCheckStatus` today; meta-title/description length are warnings, not blocking errors.
- **New code for S00** operates entirely on `blocks: InsightBlock[]` and never touches `factCheckStatus`, `slug`, `sources`, `claims`, `metadata`, or URLs:
  - [`src/lib/admin/core56-hygiene.ts`](../src/lib/admin/core56-hygiene.ts) — pure detectors + transforms (Tasks B/C).
  - [`scripts/insights-audit-core56.ts`](../scripts/insights-audit-core56.ts) — read-only audit (Task B), `npm run insights:audit-core56`.
  - [`scripts/insights-remediate-core56.ts`](../scripts/insights-remediate-core56.ts) — dry-run (default) and staging-write remediation (Tasks D/E), `npm run insights:remediate-core56`.
- **Reused existing patterns** rather than reinventing them: the raw-`postgres` read/write style, transaction-per-article, `workflow_events`/`admin_audit_logs` writes, and `DATABASE_TARGET`/`CONFIRM_PRODUCTION_*` gating all mirror `scripts/core56-publish.ts` / `scripts/insights-backfill-import.ts`. `tiptapDocumentFor` was exported from `insights-backfill-import.ts` so the write path keeps `editor_document` in sync with edited `blocks`.

Per the sprint's own safety rule ("if environment identity is uncertain, stop before writes and report BLOCKED"):

- `.env.local` in this checkout sets `DATABASE_TARGET` twice (`staging`, then `development`), and its `CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_HYPERDRIVE` is byte-identical to the production `DATABASE_URL` in `.env.production.local`.
- The `DATABASE_URL` actually resolved in this session points at the **same host recorded in `.env.production.local`** — i.e. production, not a staging branch. (The literal hostname is deliberately omitted from this doc and from generated reports since it's an infrastructure identifier; anyone with repo access can confirm it locally by comparing `.env.local`'s resolved connection against `.env.production.local`.)
- The audit and dry-run commands are **read-only** and were safe to run against this database. **`--write` was never invoked.**
- `insights-remediate-core56.ts --write` independently requires `DATABASE_TARGET=staging`, `--target=staging`, and `--confirm-staging-host=<substring>` that must match the actually-resolved DB host — this would correctly refuse to run against the current environment as configured, since `DATABASE_TARGET` doesn't resolve consistently and the host is production.
- **Before anyone runs `--write`**: confirm the real staging Neon database/branch independently (e.g. `wrangler hyperdrive list` cross-referenced with the Neon dashboard), fix the `.env.local` contradiction, and only then supply a verified `--confirm-staging-host`.

## 6. Two real detector bugs found and fixed during verification

Task A explicitly calls for confirming exact counts rather than trusting the audit prompt. Doing that surfaced two real bugs in the first draft of the detectors, both fixed and covered by new tests before any numbers were reported:

1. `blockPlainText` only handled `paragraph`/`heading`/`bullet-list`/`numbered-list`/`quote`/`direct-answer`/`callout` blocks, so leaked phrases inside `cta`, `checklist`, `steps`, `evidence`, etc. blocks were invisible to the phrase-leak detector (it reported 0/56 on the first run). Fixed by extending `blockPlainText` to cover every text-bearing block type.
2. `detectMarkdownPipeTableParagraphs` assumed a markdown table lives inside one paragraph block with embedded newlines. The real Core 56 import shape is **one paragraph block per table row** (confirmed by inspecting TC-007's published snapshot directly). Fixed by detecting contiguous runs of single-line pipe-row paragraph blocks, not just multi-line single blocks; `convertMarkdownPipeTableToBlock` now collapses the whole run into one `comparison-table` block.

A CTA-remediation ordering issue was also fixed: `removeInternalWorkflowPhrases` and `replaceDraftCta` could both touch the same CTA block, leaving a stale "would become empty" manual-review note even after `replaceDraftCta` successfully replaced it. `cta` blocks are now excluded from the generic phrase-stripper — `replaceDraftCta` is the single owner of CTA remediation.

## 11. Rollback plan

- Nothing is published or approved by this sprint's write path — reopened articles sit in `draft` with `publishedSnapshot` untouched, so the live site is unaffected regardless of what happens to the draft.
- Every write is one transaction per article with `admin_audit_logs`/`workflow_events` rows recording `transformationVersion: "core56-s00-hygiene-v1"` and before/after checksums, so a bad batch can be identified precisely and each affected group's `draft_snapshot` restored from its most recent `insight_article_revisions` row (immutable, untouched by this sprint) via the existing `restorePublishedRevision`-style admin flow.
- `npm run insights:verify-database` and `npm run insights:audit-core56` are safe to re-run before/after any real write to diff exact counts.
